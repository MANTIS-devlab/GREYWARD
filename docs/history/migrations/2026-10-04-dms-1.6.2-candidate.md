# DMS 1.6.2 candidate implementation evidence — 4 October 2026

Historical development evidence, not release acceptance. Current gates and
ownership remain in the [active migration tracker](../../architecture/DMS_1_6_MIGRATION_PLAN.md).

## Source and recoverability

Implementation used the real dirty working tree on `codex/dms-1.6-migration`.
Before edits, 238 working-tree entries and 4,136 source-file hashes were recorded
with a private ZIP and diff under ignored `output/dms-migration/baseline/`.
Unrelated Security Center and branding work was preserved; no broad commit/reset
was performed.

The Fedora 44 development guest `.149` matched the supplied UUID and MAC. SSH,
logs, IPC and automated captures were authorized; graphical-console selection
was not a blocker. No host checkpoint or clean-image acceptance is claimed.
Restrictive archives retained the legacy payload, wrappers, units/drop-ins,
config/state/cache, preferences and greeter inputs. A file restore rehearsal
matched the old binary. An actual runtime rollback later restored 1.5.3, its
notification owner, original plugin preferences and Secure widget bytes; the
candidate was then reactivated. Modified user plugins were preserved for review.

The compatibility tuple was Quickshell 0.3.1-2.fc44, Labwc 0.9.6-1.fc44,
UWSM 0.24.3-1.fc44 and separately packaged DMS Greeter 1.6.0-1.fc44.
SELinux remained enforcing. Swaylock/swayidle/wlopm were absent initially and
installed for a separately labelled normalized baseline. The external dgop
package was retained for old-runtime rollback, although the candidate does not
depend on it. Hyper-V daemons were added for guest acceptance; pre-install idle
measurements therefore do not establish a fully identical workload comparison.

## Lock incident and regression fixture

The upstream custom-lock bookkeeping and deduplicated logind state suppressed
repeated lock requests. A narrow QML patch subscribes to typed logind Session
Lock signals through the existing DMS D-Bus interface. A failing simulated
locker received three successive logind requests and a fourth direct DMS lock
request. DMS's own session-lock secure/locked state remained false. Cleanup
restored the fixed production wrapper and cleared request bookkeeping.

An earlier test terminated a real swaylock process. Labwc correctly retained
its protected surface, leaving a black screen. Recovery restarted the graphical
session through UWSM; greeter/login logs and an automated capture confirmed the
desktop returned, and the user confirmed the screen was back. This is neither
a successful password-unlock test nor proof of suspend/resume behavior. Further
failure testing used a simulated locker; no Fedora PAM/authselect changes or
DMS authentication synchronization were performed.

## Performance and remaining acceptance

Ten candidate warm service starts, ten restarts and thirty open/close IPC cycles
per launcher/settings/notifications/control-center/power-menu were collected.
Startup-to-settings-IPC median/p95 were 4,053/4,340 ms; restart 4,045/4,136 ms.
Panel IPC p95 ranged from 74 to 142 ms. These measure protocol completion,
not the first rendered frame or keyboard/mouse interaction latency.

The original idle baseline's combined RSS median was 580,554,752 bytes, and the
normalized 1.5.3 baseline 542,380,032 bytes. Both had roughly 0.20% median
live-process CPU of one core. These initial CPU measurements omit exited
helpers and are superseded for comparison by cgroup-v2 CPU accounting. A
candidate run after panel cycling recorded a 55% CPU spike and
699,256,832-byte RSS median, with surface activity/reconnection logs during the
measurement. Its complete sample is retained; it does not pass a controlled
idle/performance budget or prove the cause. A fresh quiet measurement and the
controlled vanilla/old comparison are recorded separately when available.

A fresh ten-minute candidate run recorded 0.200% median / 0.399% p95 live-process CPU and
507,453,440-byte median / 509,550,592-byte p95 RSS. A matching normalized old
protocol run recorded startup p95 3,836 ms and restart p95 3,782 ms. Against the
first candidate run, startup increased 13.1%, exceeding the 10% allowance;
restart and panel IPC remained within their allowances. These are preliminary
protocol results, not rendered-latency or full performance acceptance.

The optimized verifier retained every integrity/ownership check while streaming
file digests and checking shared ancestors once per invocation. Its candidate
protocol startup median/p95 were 4,007/4,239 ms, restart 4,044/4,233 ms. Against
the first normalized old run, startup/restart still marginally exceeded the
10% allowance; no budget waiver or promotion is implied.

The requested old/new/old protocol check completed before wrap-up. The repeated
normalized 1.5.3 run measured startup median/p95 4,036/4,272 ms and restart
4,118/4,664 ms. The optimized candidate falls within the allowance against this
repeat, while exceeding it against the first old run. Baseline variability
therefore remains unresolved; these results do not establish a performance
pass. The customized candidate and idle coordinator were restored and active
at handoff.

The matched ten-minute post-cycle runs using cgroup-v2 accounting recorded:

| Runtime | CPU median / p95, % of one core | Combined RSS median / p95, bytes |
|---|---|---|
| Normalized 1.5.3 | 5.307 / 7.120 | 866,271,232 / 867,540,992 |
| Customized 1.6.2 | 0.203 / 2.217 | 584,966,144 / 589,180,928 |

These runs observed about 32% lower median RSS and substantially lower CPU
including exited helpers. They do not establish full rendered-latency, repeated
reference-growth, hardware or four-way acceptance. The user requested wrapping
up instead of extending testing for hours; further long vanilla/original runs
were left pending. Embedded vanilla startup had already passed separately.

Promotion remains blocked by incomplete controlled performance/rendered-latency,
visual/taskbar/scaling/hotplug, genuine PAM unlock/wrong-password/suspend,
fresh production installation, physical hardware, external-request/privacy and
complete license/SBOM gates. Missing evidence is unvalidated. Previous artifacts
and state backups remain recovery inputs.

## Subsequent user correction: native DMS locking

Later on 4 October the user rejected the plain grey swaylock screen and selected
native DMS locking as canonical. This supersedes the external-lock decisions and
simulated external-lock results above; those remain historical evidence only.
The source contract is now in the active migration tracker.

Installed `.149` packages are `greyward-session-0.1.0-3.fc44.noarch` and
`greyward-dms-1.6.2-4.fc44.x86_64`. The native lock QML is unchanged upstream;
the patchset now touches nineteen files. The session RPM owns the keyboard wrapper,
user unit, defaults and PAM service. Native authentication includes Fedora's
existing system-auth stack, without changing authselect, login or greeter PAM.

Observed acceptance: offline DMS package build and backend tests passed; all sixteen
migration/lock-confirmation tests and five root-owned integrity fixtures passed
on Fedora. Both repository gates passed. Installed RPM verification reported no
drift, API 34/internal sampler/shell IPC returned READY, the effective AC/battery
lock and monitor settings matched source, the DMS sleep-delay inhibitor was active,
and no swaylock/swayidle process or enabled legacy idle coordinator remained.
The shell was active with zero automatic restarts after the final package switch;
all four first-party plugins loaded. SSH and greetd remained active.
The VM's older Labwc configuration lacked Super+L; the canonical wrapper binding
was added after a private backup and applied with `labwc --reconfigure`.

Deployment did not reboot, suspend or trigger a real lock. Authenticated unlock,
wrong-password rejection, repeated locking and suspend/resume remain manual
acceptance, together with the existing fresh-image/hardware gates.
